# Android signing and release procedure

## Current configuration

- Android application ID: `com.bizpro.vickins`.
- Production EAS profile: `production` in `eas.json`, with `credentialsSource: local` and `autoIncrement: true`.
- EAS production signing is configured with `credentialsSource: local`; EAS CLI reads `apps/mobile/credentials.json` and its referenced keystore before sending a build to EAS.
- The ignored local credentials file uses `android.keystore.keystorePath`, `keystorePassword`, `keyAlias`, and `keyPassword`. The referenced keystore must remain outside Git and outside the EAS project archive.
- The Android native directory is ignored by Git. A clean checkout's ordinary Expo debug build uses the debug signing key generated by Android tooling; production release builds should use the documented EAS production profile.

## Local development

Use `pnpm --filter @vbo/mobile android` for a debug build; no production credentials are required. Do not use release signing material for routine development.

For an explicitly authorized local release build, provision a protected copy of the approved keystore and credentials in the ignored `apps/mobile/credentials/` directory, then run the pinned EAS CLI against the `production` profile. Do not put secrets in shell history, source control, `.env` files, build logs, or screenshots. Keep a separately protected recovery backup controlled by the release owner.

## Protected CI release build

The manual GitHub Actions workflow `.github/workflows/android-production-build.yml` targets the protected `android-production` environment. A repository administrator must configure environment protection (required reviewers) and add these environment secrets before using it:

- `ANDROID_KEYSTORE_BASE64`: base64 encoding of the approved `.jks` file.
- `ANDROID_KEYSTORE_PASSWORD`.
- `ANDROID_KEY_ALIAS`.
- `ANDROID_KEY_PASSWORD`.
- `EXPO_TOKEN`: a least-privilege Expo access token for the linked project.

The workflow materializes the EAS local-credentials files only on the ephemeral runner, keeps their paths Git-ignored and EAS-ignored, and triggers a signed EAS production build. EAS uses `EXPO_TOKEN` for project access and local credentials for Android signing. It does not submit or publish the artifact to Google Play. A release owner must review the resulting EAS build and submit it through the approved release process. Do not add the exposed key as a CI secret; provision only a key whose role and remediation are approved.

## Determine the exposed key's role before replacement

The repository's JKS contains a private-key entry, and its public certificate matches the tracked `upload-certificate.pem` by SHA-256 fingerprint. This verifies the pair only; filenames and repository configuration cannot establish the Play Console role.

The Play Console release owner must open the app's **Play app signing / App integrity** page for `com.bizpro.vickins` and compare the displayed **Upload key certificate** and **App signing key certificate** fingerprints with the repository certificate. Also confirm whether Play App Signing is enabled and check signing identity for the currently published app. Do not delete or replace the existing local keystore until this check and a recovery plan are complete.

- If this is the **upload key** for a Play App Signing app, create a new upload key, export its public certificate, request an upload-key reset in Play Console, wait for Google's reset to take effect, validate a signed bundle against the approved upload certificate, then replace the protected CI/local credentials and secure the new recovery backup. Upload-key reset does not change Play's app-signing key.
- If it is the **app-signing key** and Play App Signing is enabled, coordinate a Play Console app-signing-key upgrade with the release owner and assess Android-version compatibility and API certificate registrations before changing builds. This is not an upload-key reset.
- If Play App Signing is **not** enabled and the exposed key is the app-signing key, do not replace it unilaterally: updates generally require the existing signing identity. Escalate to the Play account owner and Google Play support to establish the available recovery path before any key change.

## Public Git history

The signing files were removed from the current Git index and are ignored for future additions, but the credential-bearing commit is reachable from the public `origin/master` history. No history rewrite or force push was performed. The repository owner must coordinate a maintenance window, notify contributors, create a verified backup, remove the credential blobs from all affected refs with a history rewrite, force-push only after approval, and require fresh clones or carefully coordinated rebases. History cleanup does not make exposed credentials safe; complete the Play key-role decision and approved reset/upgrade separately.

## Release validation checklist

Before production use, the release owner should:

1. Complete the Play Console key-role review and reset/upgrade plan above.
2. Configure required reviewers and protected environment secrets in GitHub.
3. Run the manual Android production workflow using only approved replacement/current credentials.
4. Compare the output AAB signing certificate with the expected upload certificate using `keytool`/`jarsigner`, without logging private values.
5. Upload to a Play internal testing track and verify update acceptance before promoting the same artifact.
6. Coordinate public Git-history cleanup and verify the signing paths are absent from all remote refs after the rewrite.

The production signing path is **not validated** until those owner-controlled Play Console and CI steps succeed.

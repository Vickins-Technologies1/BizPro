## Architecture findings

- Mobile is Expo / React Native with Zustand, SQLite-backed persistence, secure storage, and an explicit offline action queue. Its API client owns normalization, shared business rules, and mobile offline-safe workflows.
- Windows is Next.js 14 rendered in Electron. It has a separate browser `fetch` API client and `localStorage` session/cache/queue. It does not reuse the mobile SQLite queue or native services.
- `apps/desktop/next.config.mjs` rewrites `/api` to a build-time `DIRA_API_URL`, defaulting to the production Cloud Run endpoint; `apps/desktop/.env.example` documents the override.
- The API has the required feature modules for much of the mobile surface, but the current desktop client exposes only a subset of those endpoints.
- Electron sets a 1024×680 minimum. The latest packaged application launched from release/win-unpacked and rendered the branded sign-in screen without a development server. Authentication and authenticated CRUD remain unverified.

## Implementation update

Desktop POS now supports editable basket quantities, flat/percentage line and order discounts, server-default tax calculation, customer credit, split tenders, local current and saved drafts, barcode/SKU lookup, offline queuing, and receipt printing. Mobile's custom tax controls remain preview-only; its recorded sales also use the server's business-default tax rate. The sales API records split tenders separately and resolves customer references by internal or external ID within business and branch scope. The supplier workspace now includes supplier/category management, related contacts and URL-based documents, payment entry/history, statements, performance, and linked purchase-order context using existing APIs and shared permissions. Customer, supplier, and expense creation use existing API routes. Offline read caches and queued writes are scoped by business and user. The queue count is reflected in the shell and dashboard. Server validation failures are not mislabeled as offline sales. Dashboard activity uses API-backed sales and expenses; notifications can be marked read; reports use API date filters with CSV export; and insights use the enterprise analytics endpoint.

Customer, supplier, and expense creation call existing API routes and enforce shared permissions. Offline read caches and queued writes are scoped to the signed-in business and user. POS server validation errors are not mislabeled as offline sales. Dashboard activity uses actual sales and expenses. Notifications can be marked read, reports have API-backed date filters and CSV export, and insights use enterprise analytics.

This update also adds `/auth/me` session revalidation after startup, a normalized API error type, and product edit, archive, stock adjustment, and history views using existing product endpoints. Desktop, API, and mobile typechecks pass. The authenticated login and dashboard were verified in the packaged app; UI Automation could not navigate further because click geometry was unavailable. No business data was mutated in the live account.

The Team screen now supports inviting a cashier or manager, suspending/restoring existing staff, editing profiles/roles/permissions, and owner branch reassignment through the current employee API. Desktop typechecking passes; these live CRUD workflows have not been exercised against a test backend.

The desktop now opens to a branch-scope workspace chooser, including owner consolidated read scope, and has an account profile/sign-out view plus a read-only subscription summary. Branch-specific write screens require a selected branch. Billing changes and profile/password editing are still unavailable from the authenticated API.

Purchase orders now support partial and final receipts in both mobile and desktop. The API rejects attempts to set a received status through ordinary edits, limits each receipt to outstanding quantities, and updates product stock, stock movements, receipt history, and order status in one Mongo transaction. A stable receipt ID makes a retried request idempotent. The focused receipt smoke and tenant-safety smoke pass; authenticated UI/database workflow verification remains outstanding, so this feature stays Partial.

Stock transfers now use draft, dispatch, and receive actions rather than status edits. Dispatch deducts available stock from the source branch; receipt adds it at the destination; each operation and its branch-scoped movement record commits in a Mongo transaction. Movement rows retain batch and serial metadata, and mobile stock history displays it. Repeated dispatch/receive requests return the existing transition without duplicating stock. The API rejects insufficient stock, unauthorized branch actions, edits after dispatch, and archival after dispatch. Both clients select branch-specific products and use their shared external catalog IDs. Old in-transit records without `dispatchedAt` are not auto-received because their source deduction is unknown; they need a deliberate reconciliation path. Focused transaction and tenant smoke checks pass, but live authenticated workflow verification remains outstanding. The new API server behavior has not been deployed to the configured production service, so the packaged desktop cannot use these actions against that server yet.

Desktop login now links to password recovery and one-time reset forms backed by the existing `/auth/forgot-password` and `/auth/reset-password` endpoints. The neutral request response and code/password validation follow the mobile flow; reset delivery and completion need a dedicated test account and delivery configuration for end-to-end verification.

Industry operations now implement the mobile order, appointment, work-order, and project workflow through the existing business-operations endpoints. The desktop uses shared industry configuration and status-transition helpers, validates dates and vehicle fields, and supports search, status filtering, assignment, item lines, progression, and cancellation. Tenant smoke and shared business-operation lifecycle smoke pass; authenticated workflow CRUD remains unverified.

Customer records now include expanded create fields, API-backed updates, and a payment-history/collection modal. Collection uses the existing customer-payment API, carries the selected branch for owner writes, enforces staff branch scope, and queues offline with an idempotency ID.

Finance now includes a paginated API-backed invoice list with search, draft invoice creation, payment recording, send, cancel, and archive actions. Invoice totals and payment rules stay on the API. The API payment route now forwards `branchId` from the query into the branch-scope resolver; the mobile client already sent this value but the controller had dropped it. Branch selection now persists by branch ID, and Settings supports branch create/edit and activation/deactivation via existing endpoints.

These features remain **Partial** until authenticated CRUD, navigation, offline restart/retry, role restrictions, and account switching are exercised against a dedicated test backend. No feature is promoted to Complete from typechecking or source inspection alone. Outstanding missing modules and workflows in the table remain in scope.

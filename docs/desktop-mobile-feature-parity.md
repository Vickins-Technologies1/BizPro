## Architecture findings

- Mobile is Expo / React Native with Zustand, SQLite-backed persistence, secure storage, and an explicit offline action queue. Its API client owns normalization, shared business rules, and mobile offline-safe workflows.
- Windows is Next.js 14 rendered in Electron. It has a separate browser `fetch` API client and `localStorage` session/cache/queue. It does not reuse the mobile SQLite queue or native services.
- `apps/desktop/next.config.mjs` rewrites `/api` to a build-time `DIRA_API_URL`, defaulting to the production Cloud Run endpoint; `apps/desktop/.env.example` documents the override.
- The API has the required feature modules for much of the mobile surface, but the current desktop client exposes only a subset of those endpoints.
- Electron sets a 1024×680 minimum. A previous standalone Windows package launched and accepted a live account login; the latest source changes still require a fresh package and launch verification.

## Implementation update

Desktop POS now supports editable basket quantities, per-line and order discounts, server-default tax preview, customer credit, split tenders, one locally persisted draft, barcode/SKU lookup, offline queuing, and receipt printing. The sales API records split tenders separately and resolves customer references by internal or external ID within business and branch scope. Customer, supplier, and expense creation use existing API routes with shared permissions. Offline read caches and queued writes are scoped by business and user. The queue count is reflected in the shell and dashboard. Server validation failures are not mislabeled as offline sales. Dashboard activity uses API-backed sales and expenses; notifications can be marked read; reports use API date filters with CSV export; and insights use the enterprise analytics endpoint.

Customer, supplier, and expense creation call existing API routes and enforce shared permissions. Offline read caches and queued writes are scoped to the signed-in business and user. POS server validation errors are not mislabeled as offline sales. Dashboard activity uses actual sales and expenses. Notifications can be marked read, reports have API-backed date filters and CSV export, and insights use enterprise analytics.

This update also adds `/auth/me` session revalidation after startup, a normalized API error type, and product edit, archive, stock adjustment, and history views using existing product endpoints. Desktop, API, and mobile typechecks pass. The authenticated login and dashboard were verified in the packaged app; UI Automation could not navigate further because click geometry was unavailable. No business data was mutated in the live account.

The Team screen now supports inviting a cashier or manager and suspending/restoring existing staff through the current employee API. This UI change passed desktop typechecking but has not been exercised against a test backend.

Customer records now include expanded create fields, API-backed updates, and a payment-history/collection modal. Collection uses the existing customer-payment API, carries the selected branch for owner writes, enforces staff branch scope, and queues offline with an idempotency ID.

Finance now includes a paginated API-backed invoice list with search, draft invoice creation, payment recording, send, cancel, and archive actions. Invoice totals and payment rules stay on the API. The API payment route now forwards `branchId` from the query into the branch-scope resolver; the mobile client already sent this value but the controller had dropped it. Branch selection now persists by branch ID, and Settings supports branch create/edit and activation/deactivation via existing endpoints.

These features remain **Partial** until authenticated CRUD, navigation, offline restart/retry, role restrictions, and account switching are exercised against a dedicated test backend. No feature is promoted to Complete from typechecking or source inspection alone. Outstanding missing modules and workflows in the table remain in scope.

# Dira OS Financial Integrity Audit — Phase 1

**Date:** 2026-10-31  
**Scope:** Static, read-only audit of the current repository state; calculation architecture and regression-test plan.  
**Execution:** No tests, migrations, database access, production data changes, payments, or provider calls were performed.

## Executive summary

The repository already has useful foundations: sales resolve item price and cost from the API database, sale creation wraps inventory and payment creation in a MongoDB transaction, a shared financial module rounds money to two decimals, and several flows carry external IDs. Those protections do not yet form one authoritative ledger.

The highest-risk paths are:

1. The authenticated sync endpoint can upsert payment rows directly, bypassing sale/invoice balance rules and changing posted payment amounts or statuses.
2. Invoice inputs and invoice edits can create invalid or contradictory totals; draft credit/debit notes immediately change receivables.
3. Customer payments are unallocated, accept invalid amounts/methods at the API boundary, and the Finance aggregate nets them across the business.
4. Finance counts payment rows without requiring successful/reconciled status; M-Pesa labels and webhook matching are not authoritative enough to establish settlement.
5. Mobile POS and server totals differ; mobile split payment details do not reach the sale API.

Findings below distinguish confirmed behavior from product decisions and implementation risks. Severity reflects likely financial impact for authenticated staff or a replay/error path, not anonymous internet access.

## Calculation and request-to-database walkthrough

### Sales and sale payments

Mobile computes subtotal, line and order discounts, tax, total, amount paid, and balance in JavaScript numbers. On submit, the store sends item identifiers, quantities, line discounts, a single payment method, and aggregate `amountPaid`. The API reloads product price/cost, applies the submitted line discount, calculates tax using the business default rate, and calls shared `calculateSale`. It persists the resulting sale, reduces stock, and records payment rows inside `runInTransaction`.

The current API calculation does not trust client totals, which is good. However, order discount, price override, manually entered POS tax, and split payment allocations do not follow the same calculation path. `paymentLines` exist in the API service and are covered by one service-level smoke scenario, but the mobile API client does not send them. Later sale payments update `Sale.amountPaid`, `Sale.balanceDue`, and a linked `Payment` row transactionally. Customer balances are also adjusted for named customers; walk-ins are represented directly by `saleId`.

### Invoices and invoice payments

Invoice line totals are recalculated in the API. The calculation uses JavaScript `Number`, quantity × unit price, a discount formula, and tax settings. Initial `amountPaid` is clamped to the calculated total but is not represented as a Payment ledger row. Invoice payment requests check `amount > 0` and `amount <= balanceDue`, then create a Payment row and update the invoice in a transaction. Invoice edits can recalculate totals while retaining/clamping the aggregate `amountPaid` and without reconciling the payment ledger or customer balance.

Invoice identity has a likely client/API mismatch: serialized invoice IDs prefer `externalId`, while the payment service looks up the route ID only as Mongo `_id`. The mobile client passes the serialized invoice ID. Invoices created by mobile with an external ID can therefore fail payment lookup.

### Customer debt and receivables

`calculateCustomerOutstanding` groups a sale with a linked invoice and chooses invoice balances when linked; it then subtracts standalone customer payments. This is intended to prevent double counting, but the IDs and lifecycle state used to form those links must be canonical. Draft invoices are currently included in analytics and Finance receivables. Standalone payments are not allocated to a particular debt. Finance subtracts their aggregate from business receivables, so customer credit can offset another customer's debt in that metric.

### Reporting and provider reconciliation

Finance sums all Payment amounts for its date/branch range without restricting status, reconciliation, reversal, or currency. This includes manually entered methods and any pending/failed-like state that reaches the collection. The Tuma webhook currently finds a payment by reference only and sets it reconciled without checking callback event type, success, business, provider transaction ID, amount, or currency. The POS itself says STK push is not connected; no live payment provider call was made or tested in this audit.

## Part B — Proposed authoritative architecture

### 1. Money representation and compatibility

- Repository convention today is major-unit JS `Number` with `MONEY_SCALE = 100`; Mongo schemas store `Number`. Default currency is KES, but currency fields accept arbitrary strings and invoices currently force business currency.
- Use integer **minor units** for calculations and payment allocations, with precision determined by a constrained currency registry. For KES, preserve the existing two-decimal convention. Do not silently apply two decimals to other currencies until supported codes and precision are approved.
- Parse external decimal strings into minor units with a strict decimal parser; reject excess fractional digits instead of floating rounding. Do additions, comparisons, and balance checks in integer-safe arithmetic. Reject values outside `Number.MAX_SAFE_INTEGER` if using JS integers; otherwise use `bigint` internally and serialize a decimal string.
- Keep existing `Number` records readable as legacy major-unit values. Add a `financialVersion`/money representation marker and explicit conversion adapter. Do not rewrite historical values until a report-only migration plan has compared before/after totals and received approval. Decimal128 is a viable Mongo storage option if the project chooses decimal major values, but API serializers and shared calculations must then avoid conversion back to unsafe doubles.
- Define line-level rounding: calculate each taxable line from the rounded line subtotal and rounded discount, apply the configured exclusive/inclusive method, round tax once per line to currency precision, then sum rounded lines. Store the tax policy/version snapshot used.

### 2. Canonical sale and invoice calculations

Create a shared pure calculation module consumed by API and mobile preview. The API remains authoritative and supplies database product price/cost and business tax policy. The module validates identifiers (at service boundary), quantity > 0, safe maximums, price ≥ 0, discounts within authorized policy, tax rate bounds, and amount paid. Client sends intent (items, tender lines, permitted overrides), not computed totals.

For sales, support negotiated prices/discounts only after checking existing business rules and role permissions. Preserve a reason/actor and manager approval when policy requires it. Pass order-level discount as an explicit calculation input and apportion it deterministically across lines for tax/cost reporting. Persist sale and stock movement plus payment allocation in one transaction.

For invoices, use equivalent validation/rounding and explicit issue lifecycle. Decide whether a linked invoice replaces a sale receivable, supplements it, or is an independent receivable. Do not require totals to match until the current invoicing workflow is confirmed; instead store a canonical receivable group and explicit adjustments/remainder when totals differ. Initial cash already received must be posted as an actual eligible payment/allocation, not only `amountPaid` on invoice.

### 3. Canonical payment ledger and allocations

Separate these concepts instead of overloading `Payment.status`:

| Concept | Proposed representation |
|---|---|
| Payment attempt | Initiated request, idempotency key, method/provider, requested amount/currency, pending/failed outcome. |
| Successful payment | Immutable posted receipt with source, actor/device, occurredAt/recordedAt, amountMinor, currency, method, providerTxnId, and audit event. |
| Allocation | Append-only rows that apply a payment to a sale/invoice obligation, or leave it as customer-specific unallocated credit. One payment may split across multiple receivables. |
| Reversal/refund | Separate immutable event referencing the original payment/allocation; never rewrite the original amount. |
| Reconciliation | Provider/manual evidence event that transitions an attempt into a confirmed posted payment. Manual confirmation is explicitly labeled and permissioned. |

Keep branch and business IDs on payment and allocation, require association consistency, and use a globally unique provider+providerTxnId. Idempotency key is unique per business/operation; store a request hash so replaying the same key with changed amount/target returns a conflict. Never store a payment merely because a client selected “M-Pesa”; it remains pending until provider evidence or a separately authorized manual confirmation.

### 4. Outstanding balances and receivables

Per obligation, derive balance from immutable entries:

`balanceMinor = totalMinor + issued debit adjustments - eligible posted allocations - issued credit adjustments`

Clamp is not the validation strategy: reject allocations/credits that exceed the current obligation unless overpayment is explicitly held as customer-specific credit. No unallocated payment may reduce another customer's debt. Business receivables sum each active receivable group once, partitioned by currency and as-of date. A linked sale/invoice group has one active representation at a time; conversion records preserve lineage and any difference.

Do not use cached `Customer.balance` as source of truth. Keep it as a derived/cache field and reconcile it from ledger events. Reports should distinguish current balance from historical as-of balances and from period cash received.

### 5. Invoice statuses and credit notes

Retain current lifecycle states only after confirming product workflow (`draft`, `sent`, `viewed`, `partially_paid`, `paid`, `overdue`, `cancelled`, `void`, `refunded`, `archived`). Drafts are not receivables. Issued/open lifecycle is separate from payment state. `paid` iff computed balance is zero; `overdue` is derived from due date and positive balance; void/cancelled exclude the obligation only after permitted reversal/refund treatment for any payments. Manual transitions cannot override computed paid state.

Draft credit/debit notes do not post. Issuance creates an append-only adjustment exactly once; void/reversal appends the compensating event and restores the right amount/customer credit. Historical reports use event posting dates, not current note status alone.

## Part C — Transaction, concurrency, and idempotency strategy

1. Verify the production Mongo deployment is a replica set or sharded cluster. Current `withTransaction` paths require transactions; checked-in deployment docs only say MongoDB is external and do not prove topology.
2. For payment posting, in one transaction: resolve and lock/check active obligation, insert idempotency-keyed receipt/event, insert allocation, atomically decrement remaining balance with a guard (`balanceMinor >= allocationMinor`), update derived cache, and append audit event. Any failure rolls all of it back.
3. Use unique indexes for `(businessId, operation, idempotencyKey)`, `(provider, providerTxnId)`, and any one-to-one active receivable conversion. Do not use provider reference as a global unique lookup.
4. For simultaneous partial payments, use a conditional update against current remaining balance inside the transaction, not a value read before transaction. Exactly one request should consume the final remaining amount; excess concurrent request fails cleanly.
5. For sale + inventory, keep stock decrement, sale, payment receipt/allocation, and customer/receivable updates in one transaction. Preserve the existing `$expr` stock sufficiency guard.
6. Webhook events should be signature-verified, provider-event-ID idempotent, state-transition constrained, matched to a pending attempt, and amount/currency/business validated. Failed events cannot create or reconcile a payment.
7. Sync may submit commands with the same idempotency contract; it must never upsert a posted payment document directly. Offline-created payment intent is pending until server accepts it; local optimistic UI must be reversible on rejection.
8. Credit-note issue/reversal and invoice conversion use the same transaction and idempotency rules.

## Decisions requiring business-owner approval

1. Which currencies can businesses use, and what precision/rounding policy applies to each? Is KES the only operational currency or merely the default?
2. What discount and negotiated-price limits exist by role, and when is manager approval/reason required? Must 100% discount ever be allowed?
3. Is `credit` a tender method, a sale settlement state, or both? It should not count as money received unless actual value was collected.
4. Is an invoice linked to a sale a replacement representation, a separate payable, or a partial representation? How should differing totals/remainders be booked?
5. Which payment statuses count as posted cash? Which payment methods can be manually confirmed, and which require provider confirmation?
6. What exact Tuma webhook signature, success event, transaction ID, amount/currency fields, and replay semantics are contractual? Current STK UI is explicitly disconnected.
7. Which invoice status transitions are permitted after payment, and what is the refund/cancellation treatment for already posted payments?
8. Should overpayments be rejected, or held as customer-specific unallocated credit? How can that credit be allocated/refunded?
9. Are draft invoice and draft credit/debit-note amounts visible only as drafts, or do any current workflows intentionally reserve credit? Current code posts their effect into reports/balances.
10. Confirm production Mongo topology and maintenance window for any additive indexes/backfill; transaction paths need replica-set or sharded deployment.

## Six-phase implementation plan

1. **Phase 1 — Audit and decisions (this document):** confirm workflows, report definitions, supported currencies, payment/provider semantics, production Mongo topology, and existing-data anomalies. No application code changes in this phase.
2. **Phase 2 — Calculation and validation:** implement one shared currency-aware calculation boundary; harden DTO/service validation; add role-aware discount/price-override policy and contract tests. Keep API authoritative.
3. **Phase 3 — Payment ledger and sales:** add idempotent immutable payment attempts/postings/allocations; pass split tenders; atomically post sale, stock, and payments; support walk-in and named-customer partial settlement.
4. **Phase 4 — Invoices and adjustments:** align invoice calculation/lifecycle; normalize invoice IDs; define sale conversion lineage; make invoice edits safe; make draft credits non-posting and issue/reversal transactional.
5. **Phase 5 — Provider, sync, and reports:** secure and reconcile provider events; remove direct payment upserts from sync; derive reports from eligible postings/allocations; isolate customer credits and define as-of/multi-currency reporting.
6. **Phase 6 — Reconciliation and rollout:** build seeded API/concurrency suites; compare legacy totals and new calculations in report-only mode; obtain approval; deploy additive schema/index changes, monitor mismatches, then enable writes gradually. Backfill only from approved mappings; never rewrite historical values silently.

## Safest order to address confirmed findings

First close direct payment mutation through sync and stop unverified records from being counted as received (A-01, A-07, A-08). Next harden invoice/customer amount validation, lifecycle, retries, idempotency, and edit/adjustment behavior (A-02 through A-05, A-09, A-11, A-23). Then establish canonical IDs and receivable grouping/allocation, including customer credit isolation and linked invoice behavior (A-06, A-10, A-19). Align mobile inputs/split tenders, discounts, and idempotent sale creation (A-12 to A-14). Finally settle money representation, currency-aware reporting, period semantics, and deploy/verify the replica-set concurrency strategy (A-15 to A-22). Run persisted-database tests before any financial schema backfill or production rollout.
